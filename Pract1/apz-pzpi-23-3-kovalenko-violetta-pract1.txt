3 ОПИС ВИКОНАНОЇ РОБОТИ
3.1 Загальні відомості про шаблони (патерни) проєктування 
Були розглянуті поняття шаблонів проєктування та їх роль у розробці програмного забезпечення. Шаблони проєктування – це підходи для вирішення типових задач, які виникають під час розробки та проєктування програм. Вони не є готовими фрагментами коду, а описують загальну ідею побудови системи або взаємодії між її компонентами.
Основне призначення патернів полягає у спрощенні розробки та підтримки програм. Вони дозволяють структурувати код, зменшити залежність між класами та зробити систему більш гнучкою. Завдяки використанню патернів розробник може швидше знаходити рішення, оскільки не потрібно щоразу вигадувати новий підхід до вже відомої проблеми. 
Найбільш відома класифікація патернів була запропонована групою авторів, яку називають GoF, тобто Gang of Four. До цієї групи входять Еріх Гамма, Річард Гелм, Ральф Джонсон та Джон Вліссідес. Вони систематизували патерни та поділили їх на три основні категорії залежно від їх призначення.
Перша група – це породжувальні патерни. Вони відповідають за створення об’єктів та дозволяють контролювати цей процес. Такі патерни допомагають приховати логіку створення об’єктів і роблять код більш гнучким. До цієї групи належать, наприклад, Singleton, Factory Method, Abstract Factory та Builder.
Друга група – структурні патерни. Вони описують, як будуються зв’язки між класами та об’єктами. Їх мета полягає в тому, щоб спростити структуру системи та зробити її більш зрозумілою. Вони допомагають об’єднувати об’єкти в більші структури та зменшувати складність взаємодії між ними. Прикладами є Adapter, Decorator, Facade та Composite.
Третя група – поведінкові патерни. Вони визначають, як об’єкти взаємодіють між собою та як розподіляються обов’язки між ними. Такі патерни дозволяють зробити взаємодію більш гнучкою та зменшити залежність між компонентами системи. До цієї групи належать Chain of Responsibility, Observer, Strategy та Command.
Область застосування патернів досить широка. Вони використовуються у тих випадках, коли в системі виникають складні взаємозв’язки між об’єктами, коли потрібно забезпечити гнучкість та можливість розширення, а також коли важливо зменшити кількість залежностей між компонентами. 
3.2 Опис обраного патерна: Ланцюжок обов’язків  (Chain of Responsibility)
Назва патерна: Ланцюжок обов’язків (Chain of Responsibility)
Тип шаблона (патерна): поведінковий
Основне призначення: патерн Ланцюжок обов’язків призначений для організації обробки запитів у вигляді послідовного ланцюжка об’єктів. Кожен обробник отримує запит та самостійно приймає рішення, чи може він його обробити. У випадку, якщо обробник не здатен виконати обробку, запит передається наступному елементу ланцюжка. Такий підхід дозволяє уникнути жорсткої прив’язки між відправником запиту та конкретним обробником.
Передумови застосування: використання даного патерна є доцільним у випадках, коли система повинна обробляти запити різними способами, але наперед невідомо, який саме обробник буде відповідальним за їх обробку. Також патерн застосовується, коли необхідно виконувати послідовні перевірки або операції над запитом. Наприклад, перевірка авторизації, перевірка прав доступу або валідація даних. Додатково, застосовується у системах, де потрібно мати можливість змінювати або доповнювати логіку обробки без зміни існуючого коду.
Переваги: патерн дозволяє зменшити залежність між об’єктами, оскільки відправник запиту не знає, який саме обробник його обробить. Крім того, кожен обробник виконує окрему задачу, що відповідає принципу єдиного обов’язку.  Також важливою перевагою є можливість гнучкого налаштування ланцюжка. Обробники можна змінювати місцями, додавати або видаляти без значних змін у системі.
Недоліки: запит може пройти весь ланцюжок і залишитися необробленим, якщо жоден з обробників не виконає обробку. Також у складних системах може виникнути проблема відстеження обробки запиту, оскільки не завжди очевидно, який саме обробник спрацював. Додатково, при великій кількості обробників може ускладнюватися розуміння логіки роботи системи, особливо для нових розробників.
3.3 Структура шаблона (патерна)
3.3.1 Опис структурних частин
Основним елементом патерна є обробник, оскільки він задає спільний інтерфейс для всіх конкретних елементів ланцюжка. Зазвичай він містить метод обробки запиту, який приймає вхідні дані та повертає результат або передає запит далі.
Наступним елементом є базовий обробник. Він реалізує загальну поведінку, яка повторюється у всіх обробниках. Зокрема, він зберігає посилання на наступний елемент ланцюжка та містить логіку передачі запиту далі у випадку, якщо поточний обробник не виконує обробку.
Конкретні обробники реалізують власну логіку, де кожен з них відповідає за виконання окремої операції або перевірки. При отриманні запиту такий обробник аналізує його та приймає рішення, чи обробляти його, чи передавати наступному елементу.
Клієнт створює обробники та формує з них ланцюжок. Також саме клієнт ініціює обробку запиту, передаючи його першому елементу або будь-якому іншому обробнику.
3.3.2 Опис взаємодії об’єктів
Взаємодія об’єктів відбувається послідовно. Клієнт передає запит першому обробнику у ланцюжку, після цього кожен обробник отримує запит та перевіряє, чи може він його обробити. Якщо обробка можлива, обробник виконує необхідні дії та може завершити обробку. Якщо ж обробник не підходить, він передає запит наступному елементу, використовуючи посилання на нього.
Процес триває до тих пір, поки запит не буде оброблений або не досягне кінця ланцюжка. У випадку, якщо жоден обробник не виконав обробку, запит залишається необробленим.
3.3.3 UML-діаграма з поясненням
  

Рисунок 3.1 - UML-діаграма
У UML-діаграмі патерна Ланцюжок обов’язків відображаються основні класи та їх зв’язки. Інтерфейс Handler містить метод обробки запиту. Від нього наслідується базовий клас BaseHandler, який має поле для збереження посилання на наступний обробник. ConcreteHandler є нащадками базового класу та реалізують конкретну логіку обробки. Кожен з них може викликати метод наступного обробника. Клієнт взаємодіє з обробниками через інтерфейс Handler та не залежить від конкретних реалізацій. Він створює об’єкти, встановлює зв’язки між ними та запускає обробку.
3.4 Реалізація шаблона (патерна)
3.4.1 Опис реалізації мовою програмування C#
У даному підпункті було розглянуто реалізацію патерна “Ланцюжок обов’язків” мовою програмування C#.  Спочатку було визначено інтерфейс обробника, який задає єдиний метод обробки. У якості запиту використовується окремий об’єкт, що містить всі необхідні дані.
Далі було реалізовано базовий клас обробника. Він містить поле для збереження посилання на наступний елемент ланцюжка, це поле ініціалізується через конструктор, що дозволяє формувати незмінний ланцюжок. Базовий клас також містить реалізацію методу обробки, яка передає запит далі, якщо поточний обробник не виконує обробку.
Після цього було створено конкретні обробники. Кожен з них реалізує власну логіку та перевіряє, чи може він обробити запит. У випадку успішної обробки ланцюжок може бути перерваний. Якщо обробка не виконується, запит передається наступному обробнику.
Клієнтський код формує ланцюжок обробників та ініціює обробку запиту. При цьому клієнт не залежить від конкретних реалізацій обробників, а працює через спільний інтерфейс.
3.4.2 Основні етапи реалізації
Було виконано створення інтерфейсу обробника. Інтерфейс містить метод Handle, який приймає об’єкт запиту.


public interface IHandler
{
   void Handle(Request request);
}


Було визначено клас запиту, який інкапсулює дані, що передаються між обробниками.
public class Request
{
   public string Type { get; set; }
}


Було реалізовано базовий клас обробника, який містить посилання на наступний елемент ланцюжка та базову логіку передачі запиту.


public abstract class BaseHandler : IHandler
{
   protected IHandler _next;


   protected BaseHandler(IHandler next)
   {
       _next = next;
   }


   public virtual void Handle(Request request)
   {
       if (_next != null)
       {
           _next.Handle(request);
       }
   }
}


Було створено конкретні обробники, які реалізують власну логіку обробки запиту.
public class AuthHandler : BaseHandler
{
   public AuthHandler(IHandler next) : base(next) { }


   public override void Handle(Request request)
   {
       if (request.Type == "Auth")
       {
           Console.WriteLine("Авторизація виконана");
       }
       else
       {
           base.Handle(request);
       }
   }
}


public class ValidationHandler : BaseHandler
{
   public ValidationHandler(IHandler next) : base(next) { }


   public override void Handle(Request request)
   {
       if (request.Type == "Validation")
       {
           Console.WriteLine("Дані перевірені");
       }
       else
       {
           base.Handle(request);
       }
   }
}


Було продемонстровано використання патерна у клієнтському коді. Ланцюжок формується шляхом передачі обробників один в один через конструктор.


class Program
{
   static void Main()
   {
       IHandler handler = new AuthHandler(
                               new ValidationHandler(null));


       var request = new Request { Type = "Validation" };


       handler.Handle(request);
   }
}


У даному прикладі запит передається першому обробнику. Якщо він не виконує обробку, запит переходить до наступного. Таким чином реалізується послідовна обробка через ланцюжок об’єктів.
